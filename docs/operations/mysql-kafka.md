# MySQL → Kafka 任务

平台使用同一容器中的独立 ape-dts 子进程运行 MySQL 任务，无需 Docker Socket、额外任务容器或 cgroup 委派。每个 MySQL 任务占用一个运行单元，共享平台容器的 CPU／内存配额。

## 准备条件

- MySQL 已开启 Binlog，具有非零 `server_id`，并使用 `binlog_format=ROW`、`binlog_row_image=FULL`。
- 连接账号具有来源表读取权限、读取 Binlog 状态的 `REPLICATION CLIENT` 权限以及复制流所需的复制权限（例如 MySQL 的 `REPLICATION SLAVE`）。连接测试成功不等于具有复制流权限；实际启动仍可能明确报权限错误。
- 来源表必须具有真实、非空主键，支持复合主键。一个任务固定一个来源数据库，不支持同一任务跨数据库选表。
- Kafka 目标连接可用。目标 Topic 可以选择已有名称，也可配置由平台创建；连接账号需有相应写入／创建权限。
- 上传具有 MySQL Snapshot／CDC、所选消息编码和 Kafka 分区确认处理能力的 Linux x86_64 制品。本轮修复包为 `ape-dts-2.0.26-cloudcanal-20261016-293a87f7-dirty-kafka-confirm-linux-x86_64.tar.gz`，SHA-256 为 `6e843cca5ce65d69cf4789a8426c418e00e29a10a968e63583df8b610d678fc9`。这是 Debian 平台容器用包，不应直接在 CentOS 7 宿主机运行。

本轮真实链路验证使用 MySQL 8.0.36 与 Kafka 3.8.0，平台服务运行于 4 核／8 GiB 的隔离 Linux Node 容器；已覆盖全量转增量、正常停启、容器突杀后新进程恢复、Broker 拒写后重放及停止后的性能历史读取。MySQL 5.7、8.4 的检查命令选择有测试，但尚未完成对应真实版本的同步验收；用户测试服务器与真实浏览器验收仍需单独执行。

## 配置和启动

1. 在数据源中登记 MySQL，完成连接测试和“检查 Binlog”；生产环境按实际证书选择 TLS，平台不会自动降级。
2. 新建 `MySQL → Kafka` 任务，选择来源连接与初始快照选项。
3. 在映射表格中添加来源表，每行选择一个或多个目标 Topic；选择消息编码并查看格式化示例。
4. 选择已上传制品，保存后运行预检。通过后启动；若包含初始快照，平台自动完成全量转增量，不需要手工填写 Binlog 文件、位置或复制客户端 ID。

升级平台仍使用既有服务器更新脚本及外部 PostgreSQL 元数据库，需要应用迁移 25、26；无需新增 MySQL 专用容器环境变量。运行目录、存储和配置持久挂载继续沿用原部署方式。升级前停止平台并备份；迁移后的回退应恢复配套数据库备份，不能只切回旧镜像。

## 停止、恢复和重新全量

- 普通停止后再启动默认续传。仅有已应用配置时，运行预检会复用该配置派生草稿，不要求先手工保存，也不清除原位点。
- 容器异常退出或重启后，通过既有恢复流程重新建立子进程，使用数据库中已确认的检查点。全量未完成时会重跑全量，并保留原先捕获的 Binlog 起点。
- 修改来源／目标或表／Topic 映射后，普通续传会被拒绝。停止任务后明确选择“重新全量”，确认可能出现重复数据；预检通过且启动请求带相同意图，才会重新捕获起点。旧运行、旧配置和重建前位点的审计记录保留。
- 调整批次、缓冲、消息编码或首次快照开关不会自行清除已存在的续传点。若要重发存量数据，仍需明确选择“重新全量”。
- 全量尚未完成时，恢复需要保持初始快照开启；不能通过取消开关跳过未同步的存量数据。
- Binlog 已过期、来源实例变化或持久位点缺失时，平台不会静默回退到最新位置。只阻断该任务，可在平台内处理；不应删除元数据库绑定来跳过检查。

源库 Binlog 保留时间应覆盖任务停止、最长全量耗时及恢复窗口。平台只读取状态，不自动修改源库保留策略。

## 交付与监控边界

该链路采用至少一次交付，不是跨 Topic 原子事务或 exactly-once。只保存 Kafka 已确认事务的 `checkpoint_position`，不把引擎接收水位当作可恢复位点。故障后可能重放；一对多部分目标成功、后续目标失败时，已成功目标可能收到重复消息，下游应按业务主键／事件语义处理。

详情显示全量／增量阶段、已确认 Binlog 文件和位置、检查点记录时间，以及既有性能历史和运行失败告警。检查点记录时间不是源事务提交时间；当前不提供未经证明的 MySQL 秒级消费延迟，不以零代替未知值。

MySQL 控制日志与普通任务日志分开：检查点文件有界轮转；全量完成证据只记录每张表的完成标志并逐行读取。运行终止后精确清理这些临时控制文件，不将其当作永久日志保存。
