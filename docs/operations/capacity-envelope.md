# 容量包络

最后更新：2026-10-12

## 已确认边界

- 单个平台容器内运行平台 Node.js 主进程及多个 ape-dts 子进程；每个任务独立管理配置、日志、检查点和 Metrics 端口。
- Docker/Rancher 设置容器总体 CPU、内存硬限额。部署示例的 **4 CPU / 8 GiB 是整个容器的总额，包含平台、日志、指标处理及全部任务进程**，不是每任务额度。
- 任务容量配置和容量预约用于准入预算；不通过子 cgroup 执行每任务 CPU/内存硬限额，也不要求 cgroup v2 委派。预算不能防止某个任务过量使用资源。
- PostgreSQL 与 Kafka 是既有外部资源，不计入平台容器限额，部署流程不创建、重配或删除它们。

历史 Phase 0 测试曾对候选进程设置 4C/8GiB，或把 Kafka 三分区的测试总额拆成每进程 1.33 CPU/2730 MiB。这是历史施压方式，不是当前生产运行模型，也不能作为安全并发承诺。历史测试和证据不因本次部署调整而改写。

## 容量准入与验证

系统管理中的运行容量 `maxRuntimeUnits` 是允许活跃运行单元占用的总预算。一个逻辑任务可能产生多个运行单元，应按实际运行单元总数设置上限，不只按任务数计数。容量预约、激活、释放仍按现有生命周期处理；容量不足应明确拒绝启动，不超配或部分启动。

配置上限前，应在客户实际 CPU、内存、磁盘、网络与真实制品上测量：

1. 平台空闲与日志/指标高负载时的开销，预留内存和 CPU 余量。
2. 单任务快照及 CDC 的峰值内存、吞吐、延迟，包含大字段、大事务和目标端背压。
3. 多任务、多 Partition 并发，以及停止、重启、故障恢复期间的资源峰值。
4. 容器 OOM、磁盘满、日志洪泛等故障对平台及其他任务的影响。

当前不能用 `4C/8GiB ÷ 单任务配置` 推导安全并发数，也不能声明固定 TPS、最大 Partition 数或最大并发任务数。容器总限额存在，不等于已完成容量认证；压测结果应记录对应制品、配置和部署环境。

当前日志摄取采用保守实现预算：单个原始数据块 256 KiB，每运行单元 stdout/stderr 合计持续 1 MiB/s、允许 2 MiB 突发，平台全局原始待处理队列 16 MiB。超限内容整块丢弃并记录安全缺口，进程输出持续 drain。这些是避免无界内存和事件循环独占的护栏，不是生产日志速率或任务容量承诺。

## Runtime Metrics 端口池

每个运行单元需要独立 Metrics 端口。部署方必须同时配置 `SCS_RUNTIME_METRICS_PORT_MIN` 和 `SCS_RUNTIME_METRICS_PORT_MAX`；数值为 `1` 至 `65535` 的整数，最小值不得大于最大值。端口池容量 `MAX - MIN + 1` 至少覆盖全部并发运行单元。

分配出的端口仅监听 `127.0.0.1`，不得发布为 Service、hostPort 或其他外部入口。平台在启动事务中使用 PostgreSQL advisory lock 串行化分配，并由活跃 Metrics 端口唯一索引拒绝内部重复占用；分配时还探测 loopback 端口是否可绑定。

OS bind 探测与 ape-dts 实际监听之间仍存在时间窗口。部署方必须为平台保留专用端口段，禁止同一网络命名空间内的其他进程占用；数据库锁和唯一索引不能替代该部署约束。

缺少任一变量、数值非法或端口不足时，平台容器仍可启动以便配置和诊断，但需要新分配端口的任务必须明确失败；不得选用范围外端口、复用活跃端口或部分启动运行单元。

## 隔离风险

子进程共享容器 CPU 和内存，一个任务过量使用资源可能影响其他任务或触发容器 OOM。平台容量预算不能实现任务级硬隔离。如必须保证任务级硬限额，应另行评估独立任务容器/Pod 及受限编排能力，而不是向当前容器授予宿主控制权限。
