# 引擎来源与兼容性

核对日期：2026-10-29。以下区分当前行为与建议中的交付方式；上游能力会演进，后续应按具体版本重新核对。

## 当前事实

- 平台管理程序与 ape-dts 是独立进程。当前平台源码和默认镜像不包含引擎，需要管理员上传制品并为任务选择。
- 官方上游 [apecloud/ape-dts](https://github.com/apecloud/ape-dts) 的当前任务矩阵没有 Kafka → Kafka 持续转发；其 [Kafka 文档](https://github.com/apecloud/ape-dts/blob/main/docs/zh/consumer/kafka_consumer.md) 描述的是关系数据库数据写入 Kafka。
- 官方确实已有 [KafkaExtractor](https://github.com/apecloud/ape-dts/blob/main/dt-connector/src/extractor/kafka/kafka_extractor.rs)，当前持续读取 Kafka 后将 payload 按 Avro 转换为内部数据对象。这里缺失的是本平台承诺的通用 Raw 转发及其 key、headers、null、fan-out 和确认/位点语义，不能概括成“官方没有 Kafka 消费能力”。
- 平台的 Kafka → Kafka Raw 任务依赖社区维护的 [CrissMagic/ape-dts](https://github.com/CrissMagic/ape-dts) 扩展引擎，不能将该功能归为官方标准能力。本地 fork 历史中，`ff79e761` 增加 Raw fan-out，`7922a524` 补充 forwarding 与交付工具；提交记录用于说明来源，不替代对应二进制的验收。
- CloudCanal JSON、fan-out、写入确认及 Metrics 等能力也必须以所用制品为准；平台能生成 INI 不代表引擎已经实现其参数。维护源码中的未提交改动不能直接作为可复现的正式发行版本。

Kafka Raw 扩展保留源消息 key、payload、headers 及其 null 语义，按全部目标写入成功后提交源位点，交付语义为至少一次。恢复时可能重复消息；不能宣称精确一次，也不承诺保留源 Partition 编号和时间戳。

## 建议的后续交付方式（尚未实施）

建议默认镜像在构建时纳入固定版本的社区扩展引擎，同时保留用户上传和任务显式选择制品的能力。部署者通过 Rancher 拉取镜像即可获得默认引擎，无需在容器启动时下载或编译引擎。现阶段尚未提供这个默认内置流程。

1. 引擎继续在独立 AGPL-3.0 fork 中维护，Console 继续作为独立管理程序运行，不把 Rust 引擎编译进 Node.js 服务。
2. 发布前将引擎改动整理为可审查提交和固定 tag，记录源码提交、构建参数、目标架构、摘要及已验证能力；镜像构建使用确定的制品，不跟随 `latest` 自动变化。
3. 使用现有制品管理模型登记内置版本，并作为新任务的默认选择；保留手动上传入口，不新增用户侧认证、手动启用或解锁步骤。
4. 平台升级保留旧任务的制品绑定和检查点。切换引擎需显式选择并受控重启，不能用升级镜像的方式静默替换旧任务引擎。内置制品在数据库中的引用必须对应可持久使用的内容，避免换镜像后旧版本消失。
5. 已知版本按已验证能力提供任务选项。自定义未知制品不能被标注为已验证；其兼容性提示不应伪造探针通过或引入繁琐的人工认证流程。
6. 维护侧 CI 验证 Raw 转发、fan-out 部分失败、Kafka 写入确认、位点提交和故障恢复；源码存在实现不等于已完成真实链路测试。

## 许可证与对应源码

平台原创代码采用 Apache-2.0；引擎及其修改版本保留 AGPL-3.0。若提供包含引擎的镜像，需随发布保留相应版权声明、许可证，并提供与该二进制对应的引擎源码、补丁和构建说明；不能用平台许可证替代引擎许可证。组合分发的义务需按实际构成和分发方式核对。

当前仓库没有将上述“默认内置”建议描述为已交付，也没有在此次文档修订中打包或发布引擎二进制。
